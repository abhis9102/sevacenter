# Security finding → ticket policy

Findings turn into GitHub Issues labelled `security-ticket`, generated by
`tools/security/tickets.py` from CI (`.github/workflows/ci.yml`). The design question is not
"ticket everything" but **when does a finding need an owner and a deadline**, versus just
blocking the change that introduced it.

| Finding | Where found | Outcome | Ticket? | Closes when |
|---|---|---|---|---|
| Secret (gitleaks) | any push / PR | CI fails | **Yes, immediately** (`severity:critical`) | A human confirms rotation. Never automatic. |
| SAST (Semgrep) | PR | Merge blocked by ruleset; inline annotation | No. The author fixes it in the PR. | n/a |
| SAST (Semgrep) | `main` (push or weekly rescan) | Alert in Security tab | **Yes**, severity label from the rule | Automatically, when the alert is fixed or dismissed |

## Why secrets are different

A SAST finding in an unmerged PR never reaches production, so blocking the merge is the whole
fix. A secret pushed to a **public** repo is compromised the moment it's pushed: bots scrape
GitHub for keys within minutes. Deleting the line, commit or branch doesn't help, because the
fix happens at the credential's *issuer* (revoke/rotate). That work needs an owner and an audit
trail, hence a ticket even when the PR is abandoned.

## Why main gets rescanned weekly

Semgrep registry rules (`p/java`, …) change over time. Unchanged code on `main` can gain
new findings, which is the main way SAST alerts (and tickets) appear on `main` at all,
since the ruleset keeps new findings from being merged.

## Dismissing a finding

False positive or accepted risk → dismiss the alert in **Security → Code scanning** with a
written reason. The ticket then auto-closes, and the reason is the audit record. Never
"fix" a finding by weakening the ruleset globally (see the trufflehog triage in `86e0dc0`).

## Safety of the ticketing jobs

- Only the ticket jobs hold `issues: write`, and they never run a scanner.
- The secret-ticket job checks out the script from the **default branch**, so a PR can't
  rewrite the tool that holds a write token.
- Scanner output is untrusted: it's rendered inside code spans, so it can't `@mention`
  people or inject markdown.
- Secrets are **redacted** (`gitleaks --redact`) in logs, artifacts and tickets.
- Known gap: PRs from **forks** get a read-only token, so secret tickets for fork PRs fail
  (visible as a red job). Acceptable while this is a single-maintainer repo.
- Tickets are public on a public repo. That's fine for the redacted data here, but in a real org
  security tickets go to a private tracker (e.g. Jira with restricted visibility).
